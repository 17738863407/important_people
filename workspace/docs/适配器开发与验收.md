# 适配器开发与验收

> 适用任务：新建、修改、移动、重命名或验收页面脚本，以及处理选择器、解析器、API、DOM、iframe、职务证据、详情页和特殊页面。执行这些任务前必须完整读取本文。

## 一、页面脚本职责

1. 一页一个脚本，一页一套经过验证的技术规则。
2. 页面脚本只保存采集和解析技术配置，不保存机构、入口网址、地区、脚本绝对位置或固定人物结果。
3. 页面脚本至少包含四位`rule_id`、实际使用的选择器/解析器/接口字段或`parse_page()`、必要的风险说明和统一执行入口。
4. 运行器通过`crawler_core.business_sources`按序号注入业务字段；自定义`parse_page()`已经实现的逻辑不得再复制成未被使用的装饰性配置。
5. 新页面必须先检查真实网页、接口或渲染DOM，再确定技术规则；不得根据机构名、域名或历史字段猜测。

## 二、统一入口与路径

每个页面脚本必须基于`__file__`向上查找项目根目录：

```python
def resolve_project_dir() -> Path:
    """向上查找项目根目录，兼容 site_adapters 下的任意层级脚本。"""
    for parent in Path(__file__).resolve().parents:
        if (parent / "crawler_core").is_dir():
            return parent
    raise RuntimeError("未找到包含 crawler_core 的项目根目录")
```

普通入口统一为：

```python
def main() -> None:
    project_dir = resolve_project_dir()
    if str(project_dir) not in sys.path:
        sys.path.insert(0, str(project_dir))

    from crawler_core.runner import run_page_adapter

    output_path = run_page_adapter(PAGE_RULE, globals())
    print(f"输出文件：{output_path}")


if __name__ == "__main__":
    main()
```

要求：

1. 传给运行器的`globals()`必须来自正在执行的实际页面脚本模块；其中`__file__`是计算真实脚本路径的唯一事实来源。
2. 站点专用入口可以保留特殊在线流程，但仍必须使用同一根目录查找、`main()`和`__main__`保护。
3. 页面脚本禁止出现`adapter_script`字段、参数、变量或关键字实参。
4. 页面脚本禁止出现项目绝对路径、`site_adapters\...\.py`脚本路径字面量、绝对`output_dir`或依据当前工作目录拼接脚本位置。
5. `PAGE_RULE`是运行器协议，可以作为模块级常量；其他用户参数放在`__main__`块并通过参数传给`main()`。

## 三、禁止硬编码结果

禁止在任何新建或修改的页面脚本中保存：

- 人物姓名列表、职务列表或姓名到职务映射；
- `STATIC_ROWS`、`IMAGE_ROWS`、`IMAGE_TABLE_ROWS`、`FALLBACK_*`等静态结果；
- `duty_by_name`、`fallback_duties()`、`build_known_duties()`等固定结果函数；
- 个人详情页、固定详情页候选数组或从快照固化的候选链接；
- 人工确认的OCR、视觉模型人物结果或历史名单；
- 绝对输出路径、快照路径和旧报告路径；
- 读取旧输出、历史报告或快照识别结果作为本次人物抽取输入的逻辑。

允许保存稳定选择器、可复现API及业务参数、JSON字段路径、页面专属正则、iframe路径、等待条件和不携带固定人物结果的解析函数。

## 四、职务证据

1. 职务证据只能来自当前在线网页、渲染DOM、可复现接口、OCR原文或经过回指验证的同次模型结果。
2. 表格、卡片、明确CSS字段和JSON页面，先取得当前人物对应的原始职务节点、单元格或接口字段。
3. 简介或段落页只能在已经定位的当前人物内容区域内匹配完整现职句；禁止扫描整页寻找`现任`。
4. 没有现职句时，使用当前人物对应的职务标签、表格列、卡片节点、文本分隔、API字段或详情页职务字段。
5. `负责、主持、分管、联系`等职责事项不是主职务，除非页面明确将其作为职务字段。
6. 无法可靠取得职务证据时，可以保留明确姓名并留空依据说明、标记人工复核或输出失败；不得凭常识补写。

## 五、依据说明的基本清洗

基本清洗只能在当前人物原始职务证据已经可靠定位之后执行。清洗后文本必须由原始证据通过明确、可复现的删除或格式整理得到，不得补全、改写、概括或创造网页没有表达的语义。

允许的清洗：

1. 删除HTML标签、制表符、回车、换行、零宽字符、不间断空格等纯排版字符，压缩空白并整理标点两侧空格。
2. 删除职务文本开头可精确识别的固定字段标签，如`职务：`、`现任职务：`、`现职：`；不得删除正文中的同名词语。
3. 当前姓名与职务文本开头或结尾完全一致时，可删除重复姓名及紧邻分隔符；禁止模糊姓名匹配。
4. 已在当前人物区域完整定位现职句后，可以删除句首`现任`和纯句末标点；不得据此扫描整页或改写履历。
5. 可以删除独立且不携带具体职务内容的状态标记，以及只说明展示顺序的附注；附注外的真实职务必须保留。
6. 简历信息只能在已经限定的当前人物简介块中依据明确句界或字段边界排除；禁止跨段落宽泛正则。
7. 职责事项只有在结构上属于独立字段、独立句或现职句后的独立片段时才可排除；不得删除嵌入正式职务名称中的有效文字。
8. 同一人物完全相同的职务片段可以去重；不同职务按网页栏目首次出现顺序合并，并使用中文全角分号`；`。
9. 对`职务标题：多人名单`结构，每个人的依据说明只保存清洗后的职务标题；名单只用于识别人名。

原则上必须保留：

- 机构全称、简称、部门简称、行政区前缀及可能区分任职主体的指代；
- 多项现任职务、跨机构任职和明确写出的兼任职务；
- 括号内职级；
- 带期限、试用期、援派来源或任职单位的挂职、援疆、援藏信息；
- 可能改变职务性质的限定语。无法确定是否冗余时保留并进入人工复核。

页面结构、字段标签、姓名重复、简历裁剪、职责边界和多栏目去重原则上在对应页面脚本处理。公共核心只承担无语义损失的格式清理；新增公共语义清洗必须作为独立任务，经多站点验证并由用户授权。

发生语义裁剪时，单脚本验收报告必须记录“清洗前原文—清洗后依据说明—所用规则”。清洗不得导致正常记录失去全部职务证据。

## 六、选择器与页面边界

1. 先定位最小稳定人物容器，再在容器内提取姓名、职务和链接。
2. 优先使用稳定`id`、`data-*`、`name`、`role`、`aria-*`、语义类名和稳定链接特征。
3. 需要文本锚点、兄弟关系、父级反查或复杂表格时，可在`parse_page()`中使用XPath；不得把XPath或中文描述写进CSS字段。
4. 避免`nth-child()`、长绝对层级、纯样式类、自动哈希类和无边界`body`。
5. `leader_region_selector=body`只有在页面专用内容边界或`parse_page()`能够严格裁剪时才可接受。
6. `detail_link_selector=a[href]`必须有明确人物区域和链接过滤，不能全页遍历。
7. 选择器写入前验证命中数量、命中文本、链接归属、目标机构和不同页面状态。

遇到复杂页面时依次：收紧选择器、增加内容边界、使用已注册解析器、编写页面`parse_page()`；只有多页验证稳定后才沉淀为新的公共解析器。

## 七、解析器与筛选词表

1. 通用解析器和站点专用解析器的正式名称以`crawler_core\parser_registry.py`当前注册表为准；未注册名称不得视为已经启用。
2. 解析器复用以页面结构为边界，不以域名或机构名机械决定；同域名不同结构必须区分，单页特例优先页面`parse_page()`。
3. 已验证解析器原则上不直接改变既有行为；行为变化应增加版本，不能为单页破坏旧页面。
4. 明确表格列、卡片字段、详情字段和JSON字段属于强结构，禁止依赖黑白名单过滤。
5. 姓名职务简历混杂、相邻文本判断、OCR和模型后处理属于弱结构，可以使用项目保留的五类词表。
6. 半结构页面优先收紧选择器或增加专用解析器，不靠全局词表补救；短词不得随意加入包含词表。

## 八、API、DOM、iframe与特殊页面

1. API与DOM以稳定、可复现并与页面真实展示一致为判断标准，不机械认为API优于DOM。
2. API直接提供姓名、职务和详情字段，业务参数稳定且可跨会话复现时优先API；依赖动态防护、一次性Token或与页面展示不一致时继续使用DOM。
3. 接口配置记录URL、方法、业务参数、必要请求头、分页、数据路径和字段映射；禁止硬编码一次性防护参数。
4. iframe先解析主页面`src`并取得真实frame内容，再执行同样的页面边界和证据规则。
5. 宽泛容器必须排除当前节点及祖先上的`display:none`、`hidden`、`aria-hidden="true"`和明确隐藏类。
6. 同页存在领导班子、董事会、外部董事、经理层、内设机构负责人等分组时，必须按标题或结构边界只抽取目标分组。
7. 遇到“机构名+职务+姓名”连续文本时，只能移除可验证的机构前缀，再按集中维护的职务边界进行最长优先匹配，最后校验姓名。

### 图片下方第一行简介

1. 定位领导正文或iframe正文，排除导航、页脚、推荐阅读、二维码、装饰图和隐藏DOM。
2. 以真实人物头像或人物卡片为锚点按DOM顺序遍历，桌面版、移动版和懒加载重复图只保留一次。
3. 只在当前人物图片之后、下一人物图片之前寻找第一个非空文本块，不得越过下一人物块或搜索整页。
4. 从第一行开头、首个逗号或明确分隔符前提取姓名；姓名只做字符、空白和中间点校验，不依赖固定名单。
5. 只在当前人物简介块中定位现职句并清洗；第一行没有现职句时，才查找明确职务字段。
6. 第二行及以后独立出现的分工职责不写入主职务依据。
7. 人物外层链接只有在确为独立人物页时才写入详情页链接。

## 九、单脚本验收闭环

每个脚本严格执行：

1. 记录真实路径、文件名、当前哈希和Git状态。
2. 记录原选择器、解析器、正则、采集方式、详情策略和历史结果。
3. 核对规则主表中的序号、机构、入口链接、地区和业务备注。
4. 在线检查当前网页、渲染DOM或接口，确认目标分组和数据来源。
5. 只修改当前脚本并保持最小范围；不得建立转换副本。
6. 清除快照依赖、人物结果硬编码、详情链接硬编码和绝对路径。
7. 执行AST语法解析和`py_compile`。
8. 在线运行当前脚本。
9. 检查当前人物原始职务证据能够回指网页、接口、OCR原文或同次模型转写。
10. 检查十二列表头、姓名、顺序、依据说明、机构、依据链接和详情页。
11. 检查隐藏DOM、错误分组、导航、公告、联系人、内设机构和重复人物噪声。
12. 与历史成功结果比较机构、姓名集合、顺序、原始证据、清洗后依据说明、详情页和人数。
13. 将差异分为预期变化、疑似回归和需人工确认；不得为保持一致而保留旧错误。
14. 生成单脚本验收结论；通过后才能开始下一个脚本。

失败、超时、页面防护和证据不足不能转化为硬编码兜底。记录原因后按任务规则跳过或交由人工复核。
